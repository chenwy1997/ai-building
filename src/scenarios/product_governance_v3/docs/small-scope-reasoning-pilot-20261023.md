## 档位事实与A/B安排

历史`rules-20261023`的冻结模型配置和真实请求均为`deepseek-flash`、`reasoning.effort=low`。通用runner默认`none`，但批处理入口覆盖为`low`；因此历史失败不是“关闭思考”这个前提下的结果。DeepSeek Responses的`none`关闭思考，`low/high/max`开启思考，`max_output_tokens`同时包括思考与最终输出token。依据：[官方Responses合同](https://api-docs.deepseek.com/zh-cn/api/create-response/)。

先运行上面的A组，检查修复后的链路及提案质量。B组建议同版本`high`，但等待A组结果和剩余额度后再决定，不自动串行购买第二组。此前代码、知识接线和检查器不同的旧轮次不能充当A组。

| 条件 | A组 | B组（待A组检查后决定） |
| --- | --- | --- |
| 固定轮次名 | `pilot-wash-tissue-low-20261023` | `pilot-wash-tissue-high-20261023` |
| 模型 | 原批次`deepseek-flash` | 相同 |
| 思考档位 | `low` | `high` |
| 规则、skill、工具和知识 | 当前同一release | 相同；期间若修改规则须重新设计对照 |
| 初始资料、末级范围、并发和资源上限 | 原快照、上述3类、并发3、原6轮/16工具/24000输出token | 相同 |
| 抽纸共同方案 | A组独立生成一次 | B组独立生成一次，不复用A组待审提案 |

这里测试的是整条生成流程的档位效果。共同方案本身也是模型输出，因此两组末级实际收到的基线可能不同，这是流程效果的一部分，不能声称末级提示词逐字相同。以后如要只比较末级生成能力，应另外冻结同一份人工审过的基线再配对测试。供应商模型别名不保证内部权重永远不变，比较时也检查响应记录的实际模型信息。

不同时改模型、提示词、工具额度或输出上限；`high`若耗尽输出token，也计入当前同资源上限下的结果，不只给B组扩大上限。`none`与`max`参数已支持，现阶段不同时开四组。

跑完检查：

1. 工程：同族基线及3个末级是否完成，实际调用档位，工具参数纠错次数，仍阻断的规则、零属性方案及截断情况。程序通过不等于属性合格。
2. 业务：属性必要性、命名简明、同义一致、同族共性和差异理由、原生字段排除、证据与专业不确定性；由人工比较，不能按属性数量或文字长度判优。
3. 成本：请求次数、响应usage中的输入/输出及可得的reasoning token、缓存情况；费用台账记录的是保守预留，真实收费以供应商账单为准。时间如需对照，用相同并发记录各组实际耗时，注意缓存、网络和服务负载影响。

三类单次比较只提供方向性信号，不能据此证明统计意义上的准确率提升。先解决明确的上下文、工具或检查器问题；提高思考档位不替代这些修复。

## 参数、累计费用与验收

`batch-rerun`新增两个显式参数，其他命令使用时会报错，避免被忽略：

| 参数 | 约束 |
| --- | --- |
| `--category-ids` | 逗号分隔的非空、无重复末级ID；必须在原批范围内，不展开上级；与`--category-id`互斥。列表排序不改变轮次身份，按原范围顺序规范化 |
| `--reasoning-effort` | `none/low/high/max`；省略沿用原批档位。档位进入冻结身份和真实请求，不能同名切换后当成恢复 |
