# 第二组五金属性选配

执行：`bun run category-attributes-governance:hardware-transfer`

纯本地任务：读取已冻结的第一包及留出计划，用本轮编写的spec.ts生成另一组30类模板。没有调用DeepSeek、京东API或启动服务。网页参考是编写期间核对的厂家资料，记录在spec.evidence与输出sources.json；运行时不重新抓取。

## 可复用过程

1. 冻结类目清单及原知识包哈希，保持原ID、名称、层级。
2. 先按上级路径明确类目对象和核心选型需要，含混之处写入issues，不悄悄改分类。
3. 从已有定义中按对象、物理量、测量条件判断适用性；同名不足以合并。
4. 缺失概念由语义执行者写完整定义；扩大对象另建ID，记录相关旧ID，不冒充原概念复用。
5. 选配只提交propertyId、revision和类目填写策略，不改定义。重复、未知定义或错误量纲由编译器拒绝。
6. 输出完整模板、旧库复用率、核心维度复用率、新增定义和未决事项。明确区分代码测试与行业验收。
7. 只冻结可复现产物；再次运行校验每个输出哈希。内容变化需要审阅并升级版本，不覆盖旧包。

本轮需求和审核来自同一执行者，留出集已转为开发参考，不报告独立准确率。核心维度标记来自本轮判断；直接采用比例只是此次选配记录，不是检索算法的召回率。第二组只读既有定义和冻结类目清单，没有复制历史候选模板充当新答案。

## 固定上下文

同一工具族的定义序列化为固定前缀，将目标、变化证据和轮次任务追加在后面。toStdText保留全部定义字段。前缀按工具族切分，跨族内容不同；当前未接入DeepSeek请求，也没有缓存命中实测。

本轮按已选配定义生成上下文，是后续开发材料；若测试独立检索，必须从测试前冻结的知识库选取，不能预先用测试答案过滤定义。

## 修改位置

- spec.ts：30类对象、需求、定义、关系与资料边界。
- build.ts：验证、编译、统计、格式限定与上下文生成；不替代语义判断。
- entry.ts：冻结、核验、JSON及可读Markdown导出。
- tests/category-attribute-transfer.test.ts：身份不变、定义隔离、工况与条件、复用口径、可逆编码回归。

下一个品类不能仅换一个名称运行。需要先在该品类抽样编写需求、核对对象并补专业概念。这里的命令只复现已完成的30类选配，不是自动泛化治理入口。
