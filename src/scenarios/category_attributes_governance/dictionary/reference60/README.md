# 五金60类参考版的收尾与验收

运行 `bun run category-attributes-governance:hardware-reference`。此命令没有模型调用、没有商品API请求，只复现本轮明确写下的知识审阅决定。

输入为hardware30-v1和hardware-transfer30-v1两份不可变包。review.ts逐类说明为什么保留或改动；build.ts负责绑定编辑、定义升版、编译验证和指标；entry.ts输出可读模板、逐项变更与冻结清单。新增品类应先编写需求和审阅数据，不往编译器添加名称匹配规则。

本轮将模板问题与商品实例问题分开：

- 模板问题：对象不对、方向混淆、核心维度遗漏、单位不明、重复字段、必要条件缺失。本轮修正。
- 商品实例问题：某型号的数值、材料牌号、试验结果、证书缺失。模板记录填写口径，不虚构实例，也不因此无限重审模板。
- 类目范围问题：三横同名类目容纳什么商品。外部厂家的单个型号不能替代业务确认，范围不明者保留草稿、从模型试跑中排除。

所有旧属性定义保持原版本；改定义升revision。替换绑定不继承旧属性的单位覆盖。需要删字段时只从新参考模板移出，旧源包不变。输出内容指纹覆盖每个文件，已有冻结版不同则停止，必须审阅并升级版本。

56类是项目开发对照就绪，不是专家独立认证。4类范围问题在结果文件中明确列出。参考标签由同一执行者编写和复核，本轮无模型性能数据。

下一步的10类开发回归计划位于trial-plan.json，未执行。核心属性、条件分支及对象错误是验收重点，不按完全相同的ID强迫模型复述答案；有依据的等义拆分、合并需人工裁定。评分标准是本项目约定，不是行业标准。通过开发回归后，再用新留出类目测试泛化。

缓存归缓存，验收归验收。active-dictionary.std.txt为定义归档，保留全部字段；未来按工具族检索后构建稳定前缀。不得把参考模板答案拼进模型请求来抬高成功率，也不应为了命中率发送无关的完整知识库。
