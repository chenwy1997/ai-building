# 五金属性包：30类开发参考

执行 `bun run category-attributes-governance:hardware-pack`，结果在 `workspace/dictionary/v1/hardware30-v1`。此入口不调用DeepSeek、京东或数据库网络服务，不启动预览服务，不修改原类目和旧交付。

本轮是由执行者直接做的一次语义整理，得到277个项目定义和385个类目属性绑定。原参考有387项，移出5项、补入3项。语义修改配置39项，枚举转开放文本21项，两项指标不是互斥分类。18个概念跨类复用。数字来自构建结果，不是对全行业属性数量的推算。

## 脚本与决策分工

- review.ts：固定参考的完整属性清单、39项修改理由、3项新增、制造商资料链接、未决问题。它是一份已做完审阅的决策记录，不是给新类目使用的名称匹配规则。
- build.ts：核验源哈希，应用明确的概念归并，生成版本化定义；编译类目绑定；为每条原属性记录保留对照。没有列入审阅清单的新字段会失败，不自动晋升成标准。
- context.ts：按原五金二级分支组织稳定定义前缀。所有定义按固定顺序输出，不含run编号、时间或选配答案。30类开发参考恰好覆盖30个分支，因此目前每包参考源只有一个样板，不能称为成熟全分支知识库。
- entry.ts：只读本地候选SQLite，盘点2258个五金末级，确定留出名单，原子写入版本目录。重复执行复用已存在的同指纹包；改变数据后不能覆盖冻结包。

历史候选中的三万多条五金记录和2374个不同名称没有被自动归并进277个定义。其余类目仍需按同样流程提议和核实，不能把有定义覆盖的30类外推为2258类已治理。

## 产物用途

| 文件 | 用途 |
|---|---|
| 查看样板.md / 查看对照.html | 人工阅读结果和逐类差异 |
| property-dictionary.json / .std.txt | 完整定义和无损紧凑版本；同ID同revision不可改义 |
| templates.json | 保留完整原类目对象、属性ID选择、编译结果、应用对象说明和原证据 |
| comparison.json | 每个旧字段的保留/归并/修订/删除及新增记录 |
| context-packs.json | 单个分支定义前缀及哈希；只用于相关行业任务 |
| unresolved.json | 仍需资料或独立业务判断的问题 |
| holdout-plan.json | 与本轮30类不相交的30类；尚无参考标签、尚未评估 |
| manifest.json | 源哈希、内容指纹、统计和状态 |

应用对象说明不覆盖标准定义；例如净质量的称量范围、适配对象和测量端点须在具体使用时明确。原始商品字段引用只是线索，不能因有链接就视为定义已获证明。

## 验收限制

本地测试检验原类目不变、记录覆盖、定义编译一致性、单位边界、压缩可逆、前缀稳定和已知错误的回归。它没有评价DeepSeek在新类目上的准确率。整理者与本轮复核者相同，不能称独立验收。

复杂范围、多工况及开放多值仍采用有明确格式的文本。本版没有实现这些文本内部的强结构化数值校验，也没有试图填写商品属性值。泛型record/range等扩展应另建协议并做迁移，而不是冒充当前number已经覆盖。

保留型号条件必填；供应信息“是否可定制”移出技术属性。O形圈应用承压条件也移出本体模板：未来选型环节仍要询问工作压力、间隙、温度、动静密封与挡圈等，移出不等于这些条件不重要。工具电池标称电压和实际随附电池容量分开；未知品牌/型号/认证不得补造。

下一步应先独立标注留出类目，再做受预算约束的按ID选配实验。遇到范围不清或缺少概念应进入提案队列，不能靠不断追加prompt和重试自动定稿。付费semantic入口暂未接入此包。
