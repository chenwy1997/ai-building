# 属性名归并规程

把历史模板里的属性名整理成一份口径固定的标准属性字典。本规程由架构师在第1批（频次前40名）实际归并后写成，判定规则来自那批的真实取舍，不是事先设想的分类法。第1批决定保存在 `decisions/batch-0001.json`，作为后续批次的参照与回归样本。

## 为什么这样切分任务

历史交付里 12,568 个属性名对应 11,796 个末级类目，其中 `材质` 一个名字有 4,180 种（说明/类型/单位）组合，`长度` 有 1,539 种。这些不是 4,180 个概念，绝大多数只是把类目名写进了说明——`螺钉材质`、`阀体主要材质`、`柜体主要材质` 的测量对象都是"指定主体部件"。所以任务是**判断哪些写法指同一个概念**，不是为每个类目重新撰写属性。

同时确实存在必须分开的东西：`螺钉公称长度` 与 `扳手总长度` 不是一回事，`公称通径DN15` 与 `铆钉杆径5mm` 更不是。规程的全部难点在于区分这两种情况。

## 输入与输出

输入是两部分，都由程序提供：

- **已累积的标准字典全文**（`property-dictionary.std.txt`）。整份放在上下文里，不做字符串召回。归并靠语义比对：新名称是否与字典中某条属性的描述对象和测量口径一致。
- **一批候选证据**（`packages/batch-NNNN.json`）。每个属性名附带：涉及末级类目数、一级类目分布、各变体的原始说明/类型/单位/格式、值样本、示例类目路径。变体按频次给出头部，再等距采样长尾，因此高频写法和边缘写法都能看到。

输出是一个 `decisions/batch-NNNN.json`，格式见下。程序按批次顺序应用，每批都在前面所有批次的结果之上判断，所以跨批次的合并是可能且必要的。

## 判定规则

### 规则1 产品名不构成新概念

说明里出现类目名或产品名时，先去掉它再看剩下的是什么。`扳手总长度`、`批头总长度`、`套筒总长度`、`托盘外形长度` 去掉产品名都是"外形总长"，归入同一条。类目已经表达了商品是什么，属性定义不需要再重复一遍。

第1批里这条规则消掉的变体最多：`材质` 的 4,180 个变体、`长度` 的 1,539 个、`安装方式` 的 845 个，绝大部分都是这一类。

### 规则2 描述对象不同则必须分开

判断标准是"测量的是这件商品的哪个部位或哪个层次"。同名但对象不同的，无论写法多像都不能合并：

- `材质`：刚性本体 → 本体材质；与介质接触的泵体阀体 → 过流件材质；服装面层 → 面料材质。三者决定的性能不同，耐介质性由过流件材质决定，本体材质证明不了。
- `净含量` 与 `净重`：内容物不含容器，商品本体净质量含容器。定量包装商品这两个值不同。

### 规则3 测量口径不同则必须分开

这是最容易漏、后果最重的一类。同一个物理部位、同一个量纲，但规定的测量方法或基准不同：

- `公称长度` vs `总长`：紧固件公称长度是否含头由头型标准决定，与实测外形总长可能不等。
- `额定工作压力` vs `最大工作压力`：两个口径，历史模板经常只填一个当另一个用。
- `额定输入功率` vs `额定机械输出功率`：数值不同且不可互相推导。
- `标称容积` vs `内容物净体积`：容器能装多少与实际装了多少。

### 规则4 分级代号不是数值

代号体系表示的是等级或规格标识，不是可运算的量：`DN15`、`PN16`、`Class150`、`IP65`、`0.6/1kV`、服装尺码 `XL`。这些必须是 text 类型，并在定义里写明不得换算为数值。

同名下同时存在代号和数值时一定要拆：`公称直径` 既有 `DN15`（管路代号）又有 `铆钉杆部公称直径`（毫米数值）；`公称压力` 既有 `PN16` 又有 `管件额定工作压力 MPa`。混用会让两个行业的选型互相污染。

不同代号体系之间也不能互换：PN 与 Class 是两套体系，邵氏A与IRHD是两种硬度方法。

### 规则5 复合写法必须拆成多个属性

一个文本框里塞多个量的，不保留为标准属性，拆到各自的属性上：

- `尺寸`、`外形尺寸`：`长×宽×高`，甚至出现 `宽×高×深` 顺序不一致，拆成总长、总宽、总高。
- `包装规格`：`18kg/桶`、`200L 桶装`、`每盒装多少袋/丸/支及单剂量`，拆成包装形式、内容物净质量或净体积、单包装内数量。

合写的属性无法比较和筛选，这是模板难填、难用的直接原因之一。

### 规则6 单位差异不拆，量纲差异必须拆

同一量纲的多个单位放进同一条属性的 `unitIds`，挂载时选定：长度的 mm/cm/m、保质期的月/天。

量纲不同必须拆成两条，契约要求每条属性只有一个物理量：`净含量` 的 kg/g 与 L/mL 分成内容物净质量和内容物净体积。

原始类型是脏数据时按正确口径定义，不迁就历史：`保质期` 有 text 变体写 `24个月`，标准定义仍取 number + 时间单位。

### 规则7 跨名称合并要主动做

不同的属性名指向同一个标准属性时直接合并到同一 ID，这是本任务的主要收益来源：

- `电压` 与 `额定电压` → 额定输入电压
- `功率` 与 `额定功率` → 额定输入功率 / 额定机械输出功率
- `净重` 与 `重量` → 净质量
- `包装形式` 与 `包装规格` 拆出的形态部分 → 包装形式

因此必须对照整份已累积字典判断，而不是孤立地看当前这个名字。

### 规则8 判不了就 defer，不硬给定义

出现以下情况记 `defer` 并写清理由，不要为了完成率硬编一个笼统定义：

- 一个名字下有多种互不相同的含义且缺少共同测量对象。`规格` 分属药品剂量、包装规格、公称尺寸、型号代号至少四类，任何统一定义都会掩盖差异。
- 描述的是客户现场条件或推荐用途而非商品固有属性，同一商品在不同场景取值会变。`适用场景` 属此类。
- 该信息可能根本不该是属性。`配件类型` 的取值实际是配件名称，与末级类目名高度重合，是否保留属于业务决策。

也可以只归并主导含义、其余部分 defer：`连接方式` 在 762 个末级里有 501 个属泵阀管路，归入管路连接形式，电气接线与数据接口的用法留给对应行业包。

## 输出格式

```json
{
  "schema": "sanheng-canonical-decisions-v1",
  "batch": 2,
  "ranks": [41, 80],
  "author": "deepseek",
  "newUnits": [{ "id": "MPa", "symbol": "MPa", "quantity": "pressure" }],
  "amendUnitIds": [{ "propertyId": "sh.geometry.overall_length", "unitIds": ["mm", "cm", "m"], "reason": "..." }],
  "newProperties": [{
    "id": "sh.pressure.rated_working", "name": "额定工作压力",
    "definition": "制造商为目标商品规定的正常连续工作压力。",
    "object": "目标商品的承压腔或工作介质通道",
    "type": "number", "unitIds": ["MPa"],
    "excludedMeanings": ["最大工作压力", "公称压力等级代号", "耐压试验压力"],
    "qualifications": ["须说明介质与温度条件", "表压与绝压不可混用"]
  }],
  "decisions": [
    { "name": "净重", "action": "map", "targets": [{ "propertyId": "sh.own.net_mass" }], "note": "..." },
    { "name": "公称压力", "action": "split", "targets": [
        { "propertyId": "sh.pressure.nominal_rating", "when": "PN或Class等级代号" },
        { "propertyId": "sh.pressure.rated_working", "when": "以MPa标示的数值" }
      ], "note": "..." },
    { "name": "规格", "action": "defer", "reason": "..." }
  ]
}
```

字段要求：

- `map` 恰好一个目标；`split` 至少两个目标且每个必须写 `when`；`defer` 必须写 `reason` 且不能带目标。
- `map` 可以附 `defer` 数组表示部分用法留待处理，每项要写 `scope` 和 `reason`。
- 本批证据包里的每个属性名都要出现且只出现一次。
- 新属性必须写 `object`、`definition`、`type`；`excludedMeanings` 用来隔离已知混淆，是这份字典防错的主要手段，不要留空。
- 修改已有属性的单位范围用 `amendUnitIds`，程序会生成新 revision，已存的 revision 保持不变。不要用新增覆盖已有 ID。

## 程序校验什么

`applyDecisions` 只做结构校验，全部语义判断都在决定文件里：

- 单位ID不可被重定义；数值属性必须有物理量且所有单位同量纲；文本与布尔属性不得带物理量。
- 已存在的 `id@revision` 内容不可变更；新增ID不得与已有ID冲突。
- 每个映射目标必须已存在于字典；同一目标不得在一个决定里重复。
- 本批范围内的属性名必须全部决定，一个名字不得决定两次。
- `split` 目标数、`when` 非空、`defer` 理由非空。

**校验通过只代表结构自洽，不代表归并语义正确。** 定义是否符合行业实际、描述对象是否分对、必填策略是否合理，都要靠品类专家在 `属性字典-专家验收.xlsx` 上逐条判断。字典发布前不得以"程序校验通过"替代专家验收。

## 已知易错点

以下是历史交付中真实出现过的错误，可作为自检清单：

1. 输入功率与输出功率混填。
2. 商品自身品牌与适配品牌混填；自身型号与适配机型混填。
3. 把 DN、PN 当数值换算成毫米或兆帕。
4. 把某个商品的采样值当成该类目的封闭枚举。值样本只是 observed samples。
5. 布尔属性把未知写成 false。
6. 把长宽高合写进一个文本框。
7. 用 `无品牌` 代替 `未知`。
8. 把包装净重当商品本体净重。

## 后续批次怎么跑

第2批起可以交给较便宜的模型执行本规程。每批把已累积字典全文放在上下文前部作为稳定前缀，当前批证据追加在后。批次之间必须串行，因为后一批要在前一批的字典上判断跨名称合并。

每批产出后先跑 `compile` 做契约校验，再抽查若干高频名的判定是否符合上述规则。与第1批同类的名字若判法不一致，属于规程执行偏差，应先修规程或补充示例，而不是逐条手工改结果。
