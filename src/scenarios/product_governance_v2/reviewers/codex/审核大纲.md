# Codex最终审核大纲 v1

生效日期：2026-10-21。用于商品治理V2的最终审核；先以文档运行，暂不封装Skill。

## 1. 职责和上下文分开

- DeepSeek负责提出属性、命名、定义、规则及修订；程序执行契约检查、计算和Excel排版；Codex判断异常、抽查及交付范围。
- 本目录只供Codex审核使用，不放进 `standards/`，不由DeepSeek的 `loadMeta()` 自动加载。
- 业务标准仍引用同一份：02建模、03取值、04证据、08命名、10完整性、11属性边界。不要在本目录再维护一套相互竞争的业务定义。
- 按运行冻结版本审核；记录标准版本、原卡hash和候选hash。新规范不能静默套到历史运行，版本改变需明确受影响范围。
- 一次审核只接受一个任务范围。没有新的证据或变更，不重复审核已完成对象。

## 2. 先分清这次在做什么

| 任务 | Codex查看范围 | 完成条件 |
| --- | --- | --- |
| 只改Excel排版 | 列顺序、行高、颜色、冻结、筛选、审核输入、原值及证据是否保留 | 文件比对及预览通过；不调用模型，不重审属性 |
| 修订现有属性 | 变更、关联单位和公式、模型异议、程序报错，再少量抽查 | 实质问题已解决或明确隔离；没有未披露的口径变化 |
| 新类目产生属性 | 公共定义一次、类目边界、遗漏线索、程序异常及抽查 | 生成和DS完整复核已有记录；异常有裁定；不把模型一致说成准确率 |
| 商品试填/归属 | 有争议的值、证据、计算和目标类目，再少量抽查 | 值能追溯；错挂有目标或缺口说明；统计分子分母可复算 |

当前任务属于哪一行，开工时就记清楚。排版不触发属性再生成，命名修订不顺带启动全类目补全。

## 3. 输入按需展开

先读取审核摘要：任务范围、版本、程序结果、变更数量、异常队列、抽查项。再读取相关字段的前后值、规则及必要证据。完整来源保留定位，按需展开，不先把所有标题、规则和历史响应全部读一遍。

可用命令（只读原数据、生成本地审核包，不调用模型）：

```sh
node src/scenarios/product_governance_v2/reviewers/codex/prepare-review.mjs \
  --before /absolute/path/original-cards.json \
  --after /absolute/path/candidate-cards.json \
  --out /absolute/path/review-pack
```

`review-summary.json`先看，`review-pack.json`按异常展开。审核包是线索和抽样安排，不是审核结论。

## 4. 审核次序

1. **核对程序检查及版本**。错误ID、类型、枚举引用、缺失绑定、过期hash先阻断对应项。程序已验证的确定性结果直接引用，不用模型再做一次同样检查。
2. **公共定义只审一次**。按显式登记的公共ID和定义hash汇总；类目绑定仍独立。相同名称不自动共享。
3. **优先看可能改变业务含义的修改**。名称、定义、描述对象、单位、必填、适用条件、数量范围、公式、字段删增和公共归属，均对照原卡及依赖判断。
4. **集中裁定模型分歧**。先确认意见引用的字段、配置和原句真实存在，再验证推理。严重度、模型数量和“通过”都不代替证据。
5. **抽查其余项目**。默认每类从未进入异常队列的属性中取2项，用稳定hash选择并记录；公共定义不在每类重复抽。抽查发现同类实质错误时只扩大到该错误模式的受影响项。
6. **统一给出一次返修清单**。同根因合并，明确属性ID、问题、证据、允许修改字段、保护项和验收条件；由DeepSeek提出修改。

高风险项目必须看，抽样不能替代。原文缺失时记录缺证，不补造事实。

## 5. 重点防错清单

- 改名是否偷换对象或计量范围：销售总包数不能改成每提包数；支持抽/张的字段不能因改短只剩抽数；单张展开等限定不能无故丢失。
- 公共/特性/SKU基础信息是否分清：尺寸、装箱含量不能因常见就公共化；交易销售单位与包装含量分别承接。
- 审单位字段时先看DS角色判断及其配套数量ID，不以“单位”“销售”字样判删除。例如每包100张的张与按箱计价的箱不同。必要的内容计数单位保留；角色不明只列疑点，不扩大成批删除。
- “本体”等名称限定仅在真实消歧义时保留；纸巾盒默认长宽高可以自然命名，测量边界留在定义。改名只检查该字段及依赖，不重审全卡。
- 是否新增重复字段，或者为消除缺证删除核心字段、降低必填、改变条件。
- 公式是否同SKU、同销售组合，因子证据及单位是否能对应；不能把乘法的前提写成必须整除，也不能无理由拒绝完整包装链。
- 改名关联到说明、配套计数单位和规则时，检查这些依赖；原始标题、来源引文和已核实数值不能被改写。
- 归属、同品和图片等结论是否真的做过相应核验；没有做过的不写成已确认。
- 商品统计先核对ID口径、SPU/SKU、启停和在售条件。商城实际挂载ID与标准字典ID分别记录，不能混用查询字段。

## 6. 如何裁定，而不被复核意见牵着走

每条意见只取以下处置之一：**采纳、驳回、交DeepSeek修复、暂缓待证**。给出能核验的简短依据。

实际回归例：

- 模型把“销售总包数”改成“每提包数”：改了范围，交DS恢复原含义；不能通过改条件必填掩盖。
- 模型声称某类配置要求每包张数：先查配置是否真有该类及该字段，不存在就驳回。
- 模型声称“各提包数之和”必然不同于“每提包数×提数”：在同质且每提含量一致时两者相等，核对条件后判断，不照单接受。
- 规则的 `inputs.unit` 写片/张/抽：这是输入单位元数据，不直接证明把单位混进数值；须检查真正的填写格式。
- finding只写“已正确、保持现状”：记为通过观察，不再安排返修。

## 7. 返修与停止

- 默认最多一轮集中返修，再仅核对修改和依赖；程序格式恢复不能冒记成新的业务审核。
- 仍有重大问题就隔离或阻断对应项，给出剩余问题，不自动连续开启整卡修复。
- 新发现的旧问题先核对是否由本次修改引入；无关问题单列后续任务，不扩大本次范围。
- 条件满足就停止：必审项有裁定、约定抽查完成、程序错误已解决或隔离、结果与证据一致、Excel校验通过。没有证据表明存在剩余风险时，不追加“再确认一遍”。
- 对外明确审了什么、抽了什么、什么未验证；不给未经人工验收的准确率结论。

## 8. 审核记录保持精简

保存：任务与版本、输入hash、程序结果引用、公共定义裁定、异常处置、抽查ID及结果、返修ID及检查结果、遗留项和交付状态。不要保存大段内部推理，不重复模型完整响应。

效率分开统计：模型请求数、缓存及耗时；Codex实际核对范围；返修轮次；排版校验。不能只用一次模型请求耗时代表整个任务，也不以局部高缓存率代替全轮数据。
