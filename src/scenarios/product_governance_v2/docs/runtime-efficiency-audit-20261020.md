## 1. 判断

模型调用本身较快，人工参与的修复、分散脚本和交付整理仍占用较多时间。当前能按类目并发完成模型阶段，但不是通用的、输入任意类目ID列表即可完成最新全部环节的无人值守入口。下一步优先收口流水线、减少重复输出和返工，再提高并发。

## 3. 模型与思考档位

实际请求和响应模型均为 `deepseek-flash`。官方在核查日将此名称对应到 DeepSeek-V4.1-Flash-1017：[模型文档](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)。

- `DeepSeek.generate()`默认effort为low；早期`attributes.ts`沿用默认值。
- 最近18类扩展、命名审核及定点修复显式使用none。当前不是全程low，更不是high/max。
- 全run的19次low请求耗时中位数35.89秒、3次输出截断；1,006次none请求中位数4.91秒。任务内容不同，这不是公平对照，不可据此宣称关思考一定提高质量或速度倍数。
- Responses支持none/low/high/max；none关闭思考。medium映射到high，并非独立的中档。[思考文档](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)

建议的阶段配置（待小样本对照验证，并非已证明的最优档）：

|阶段|建议|
|---|---|
|既有规则下结构整理、命名候选、类型检查修复|none|
|明确边界的候选和完整卡生成|先保留none；观察结构与业务返工率|
|每类完整语义审核|优先试low，衡量能否减少后续修复总成本|
|跨层包装计算、边界冲突、仍未解决的少数语义问题|按异常升级high；无证据问题不能靠高思考补事实|
|常规批量|不默认max|

比较应选同样的类目和输入，统计总费用、总时长、程序一次通过率、需要Codex改判的问题及修复轮数，不能只比较单次请求便宜与否。若做对照，计入既有¥50预算，只跑小批，不全量重跑。

## 4. 缓存利用率与可改进处

当前全程34.5%、扩展41.3%、命名25.6%，有收益但不高。过去6件同类商品初填的小实验曾达76.41%，不能将其当成当前属性建模的命中率。

当前已有：固定业务标准、JSON稳定序列化、商品资料后置、本地完成断点复用。仍有以下缺口：

1. 不同脚本的system开头角色句不同，位于大段共享准则之前，跨脚本公共前缀被打断。应使用同一个上下文构造器，把任务角色和具体动作后移。
2. `fixedPrefixInput`在类目卡片之后才放stage/task；适合同类商品重复填写，但卡片跨类不同且修复时会变。应按“稳定核心准则→公共定义和参考资料→类目边界→阶段动作→变化字段/商品”分层，不能把全部东西都叫固定上下文。
3. 商品分组预热调度器已用于部分试填，但属性生成/命名仍直接使用普通pool。可用前两个真实待办建立共享前缀，再放开并发；要实测缓存与吞吐的取舍，不发空请求预热。
4. 输出没有缓存折扣。当前Responses约¥30.1944中，输出约¥14.2474；缩短重复定义与重复完整卡输出同样重要。共享定义可由代码从版本库装配，模型输出引用及本类绑定；这需要改输出契约和校验，当前尚未实现。
5. 调整布局必须同时查找历史旧布局的完成响应；规则内容变更则明确建新版本，不能静默把不兼容旧结果当新结果，也不能为命中率重跑已完成项。

缓存要求前缀已落盘并完整匹配，且为尽力服务，不能承诺100%。Responses的prompt_cache_key/retention参数不支持，不能靠添加它们解决。依据：[缓存规则](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)、[Responses兼容性](https://api-docs.deepseek.com/zh-cn/guides/responses_api/)。

## 5. 已串联与尚未串联

|能力|当前实际情况|
|---|---|
|单个父类ID展开末级|有，`cli.ts`/`prepare()`|
|ES在售随机样本及标题规格详情|有，采集并发固定3|
|错挂样本隔离→维度→完整卡→程序检查→完整审核→最多2轮修复重验|有，类目之间并发，类目内按依赖串行|
|预算、请求与结果断点、原始证据、成本|有|
|原CLI并发配置|有，`--concurrency N|auto`和`--max-concurrency`；初始auto=8|
|本次实际扩展脚本并发|固定6，没有继承CLI参数|
|公共定义先确认再复用|扩展使用已确认试点公共定义；还不是通用公共候选生成阶段|
|本地震坤行、命名、最新专项处理|已在本批运行过，但散落在专用脚本中，原CLI未集成全部最新环节|
|类目ID列表、父子重叠去重|原CLI没有|
|任意业务范围默认运行|没有；pilot名称和扩展门槛围绕当前清洁纸品试点|
|全部最新阶段自动汇总Excel|没有；需准备、导出和检查脚本|
|任意模型工具自主循环|没有；现阶段是代码控制工具与阶段|
|完整通过后线上发布|没有，也不应把模型通过视为上线授权|

原CLI自动扩并发是在每完成8个**类目任务**后增加，不是每8次请求；任意异常都会降速，业务JSON错误也被当成限流处理。应分开“网络/限流”与“结构/语义”错误，不让业务错误无谓降低其他类目吞吐。搜索/抓取尚无独立全局限流器，不能把规范要求当成已实现。

原CLI命令确实存在，但当前旧run的标准已经冻结；直接用最新标准恢复会被版本检查拒绝。这是保护，不应通过覆盖frozen文件绕过。新版任务需要明确revision与共享预算绑定，不能新开目录悄悄重置累计预算。

## 6. 属性是否有业务结构，公共属性是否优先

当前有outline、维度及purpose、候选定义、bindings、rules、provenance；完整卡要求维度覆盖全部属性。扩展提示明确要求对象识别→采购区别→包装计量→可选特性，符合样本才进入卡片阶段。因此不是只有平铺名称列表。

局限是跨属性依赖尚不都用可校验ID表示，部分数量/单位关联仍依靠规则文字；维度有结构也不能保证语义合理。应增补显式配套单位、条件依赖与公式依赖，程序检查不存在ID、循环及单位不一致，再让模型处理语义。

已登记共享的公共定义只有common.brand和common.model。部分历史卡还有标为“公共属性”但未登记跨类共享的字段，这些仍按类目限定存储，不能混同。公共阶段应优先定易复用识别属性，再给本类设置适用、必填和层级；颜色/尺寸不能仅因名字常见就统一。

新增 `standards/09-generation-order.md` 与已有命名规范一起由loadMeta自动收录，供**新版本任务**实际使用；不改变历史冻结请求。

## 7. 推荐实施顺序

### 第一优先：把当前正确方法接到唯一入口

一个manifest定义类目ID列表、并发、阶段思考档、预算账本、标准版本；父类展开末级并去重，公共定义先行，每类共享同一流水线。将本地参考适用性、命名准则、证据/范围约束从一开始纳入，减少产出后全批返工。不同脚本不再各自定义role、努力程度和并发。

目标接口（**设计示意，当前未实现，不可直接执行**）：

```text
bun src/scenarios/product_governance_v2/cli.ts run \
  --category-ids <父类或末级ID1,ID2> --concurrency 8 \
  --profile balanced --revision <版本名> --budget-run <既有预算run>
```

自动流程应到“汇总待裁定结果与异常”为止，导出候选不标成已运营验收。Codex处理异常与抽查；样本/本地资料不足要明确状态，不默默跳过。

### 第二优先：少发恢复请求、少输出重复文本

一类完整语义审核一次；程序结构问题先做明确且无损的本地修复；语义修复仅返回受影响内容，审核剩余未决项。公共定义由代码装配并检查hash，不强迫模型每类复述。模板命名等确定标准前置，不能周期性全量重审来弥补入口缺规范。

### 第三优先：稳定前缀和温和提高并发

稳定共享角色与准则前缀，明确阶段schema，真实待办预热后用8并发，观察12并发是否更好。只对就绪独立任务并行；21类不需要接近供应商数千并发上限。按阶段记录缓存命中率、P90、业务修复率、预算，而非只看请求成功率。
