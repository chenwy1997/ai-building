## 1. 已确定的边界

1. 新业务目录为 `src/scenarios/product_governance_v2`，模型提供方只使用 DeepSeek 官方 API。
2. 先重新制定清洁纸品的类目属性，后续再做商品归属、属性值填写与回归验证。
3. 复用旧版建模结构，不向生成或评审阶段提供旧 21 类属性答案。旧答案保留为冻结产出后的比较集。
4. 属性字段类型继续使用：文本、数值、是否、选项、日期。选项即枚举。
5. 保留公共/特性属性、SKU/SPU 承载层级、必填性、口径、规则、公式与来源。
6. 属性价值依照正确归类、参数展示、搜索筛选判断。核心必填不因数据难取而降级。
7. 标准与运行记录分离；新任务取最新已发布标准，旧任务固定版本并可追溯重验。
8. 审核分工已确认：DeepSeek 产出 → 程序检查类型、枚举和公式 → DeepSeek 专项复核 → Codex 集中裁定异常并抽查；普通合格项不再由 Codex 逐条重做。业务验收仍由用户和运营抽检。
9. 允许使用少量真实商品标题、规格辅助建模；源商品可能错挂，须先判断样本是否符合类目边界，不能将挂载类目当作已验证事实。缺失资料不能作为取消核心属性的依据。
10. 网络参考按业务分组集中获取并共享证据，仅为未解决的定义、单位或边界问题追加查询，不逐属性重复联网。
11. 21 类每类完整语义复核一次，检查遗漏、重复、计量口径和必填理由；修改后只重验受影响部分。Codex 的异常裁定和抽查不替代这次完整复核。
12. 先做软包抽纸、湿纸巾、纸巾盒，每类使用 10 件原始标题和规格辅助建模；先筛除明显错挂或归属不明的参考样本，记录排除和实际可用数量，不补造样本。完成三类属性卡、反例检查、成本和耗时报告，修复共用问题后再铺满 21 类。
13. 本次 21 类属性建模全过程累计预算上限为 50 元人民币，覆盖技术试调用、生成、复核、修复、搜索和抓取；重启和断点恢复不重置总额。并发任务发出前预留费用，达到上限保存断点，不自动追加。

## 3. API 实施选择

**首选 Responses + 本地业务校验，业务层只调用统一的 generateStructured。**

当前官方 Responses 已支持 `text.format=json_schema`；Chat 使用 `json_object`，仍需客户端 Schema 校验。新目录的输出都是结构化属性卡，优先利用 Responses 的结构约束。Schema 只能约束结构，无法保证属性合理或引用真实。

Responses 同样无状态，不能依靠 `previous_response_id` 保存流程；由本地保存阶段产物。Flash 的内置 `web_search` 不生效，搜索与抓取走独立接口；工具调用次数上限由本地执行。首个小规模技术验证若发现实际兼容问题，保留相同业务契约改用 Chat，并记录原因。

统一调用器的职责：凭据读取、完成状态检查、结构解析、用量记录、超时分类、有限重试。业务流程不用知道 HTTP 协议细节。

| 能力 | 官方接口 | 首期用途 |
|---|---|---|
| 结构化生成 | POST /responses | 候选、属性卡、语义复核 |
| 网页搜索 | POST /v1/tools/search | 获取参考资料线索 |
| 网页抓取 | POST /v1/tools/fetch | 保存可引用正文 |
| 余额查询 | GET /user/balance | 启动检查、预算告警 |

模型建议从官方 `deepseek-flash` 开始；明确设置思考强度与输出上限。机械归一交程序完成，必要的模型转换可关闭思考；建模先测 low，疑难项再比较 high。不是所有阶段都开启高强度思考。请求名与响应模型名分别留存，别名不能保证模型版本固定。

依据：[Responses API](https://api-docs.deepseek.com/zh-cn/api/create-response/)、[兼容指南](https://api-docs.deepseek.com/zh-cn/guides/responses_api/)、[Chat API](https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/)、[搜索与抓取](https://api-docs.deepseek.com/zh-cn/guides/search/)、[余额](https://api-docs.deepseek.com/zh-cn/api/get-user-balance/)、[思考模式](https://api-docs.deepseek.com/zh-cn/guides/thinking_mode/)。

## 4. 单一建模来源：定义、绑定、规则分离

借鉴 FBM：一个可序列化的业务元数据源，派生校验器、模型上下文、工具说明和导出视图，不复制多份定义。借鉴对象、关系、动作与流程状态，不移植 UI 或整套服务器。

| 对象 | 主要内容 |
|---|---|
| Category | ID、父 ID、名称、类目边界、基线版本 |
| AttributeDefinition | 稳定 ID、名称、定义、描述对象、公共/特性、字段类型、单位、排除含义 |
| CategoryAttributeBinding | 类目 ID、属性 ID、必填及条件、SKU/SPU、用途、适用范围、采用理由 |
| ValueRule | 输入、计量口径、直接取值、转换/公式、前提、冲突与缺失处理、正反例 |
| SourceRecord | 来源类别、平台、定位、摘录、获取时间、内容摘要哈希、核验状态 |
| ReviewFinding | 被评对象与版本、检查项、结论、理由、证据、建议修改 |
| StageArtifact | 任务、阶段、输入版本、上游产物、输出、未解决项、下一阶段条件 |

属性规则必须引用已登记的算子，例如单位转换、同口径除法、枚举匹配。模型可以提出新规则需求，不能生成任意代码交给运行器直接执行。

共同定义与绑定需避免重复展开：定义中不再嵌一份完整绑定后又另外传一次 bindings。属性卡由关联关系生成。

已核对的借鉴位置：本项目 `product_governance/domain/types.ts`、`domain/ontology.ts`、`domain/engine.ts`；参考项目 `/Users/sanheng/Project/sanheng/sanheng-pm` 的 `docs/norms/fbm-pattern.md`、`lib/fbm/ontology.ts`、`lib/fbm-apps/fbm-tool/read.ts`、`lib/fbm/process-position.ts`。建议工具保留 `attributes.definition(id)`、`attributes.rules(id)`、`categories.get(id)`、`sources.read(ref)`、`jobs.position(id)` 等业务命名，由同一元数据派生契约。

旧批次的具体开销线索：抽查一个 5 件商品输入文件，属性部分约 17,204 字符，另传绑定约 7,421 字符，条件约 8,324 字符，品牌词典约 6,416 字符。它们不是现金成本或 token 统计，但说明重复与无关上下文值得先消除；仅换模型和提高并发不会自动解决这些问题。

### 例：属性不是名称列表

以软包抽纸为例，先梳理业务维度：识别 → 材质/结构 → 使用特征 → 尺寸 → 包装/计量 → 采购筛选。

“包装/计量”进一步拆出单包的抽数/张数、包数、销售组合等候选；每个候选都要说明描述什么、为何需要、与前面属性有什么关系。不能将抽数、张数、层数混成同一个数量，也不能直接把整箱总张数填入单包字段。

这是过程示例，不是提前确定的属性答案。品牌可以是公共定义；香型、颜色是否适用、是否必填，要看具体类目与用途，不能因为常见就全树必填。SKU/SPU 层级同样由属性和类目绑定确定，不能简单认为公共属性全部属于 SPU。

## 5. 来源与评判如何建模

来源拆成两个维度，避免把“网络”与“京东”混成互斥分类：

- 来源类别：模型提出、本地参考词典、官方标准/厂商资料、电商页面、商品源样本、业务人工确认。
- 来源平台：DeepSeek、震坤行、京东、淘宝、拼多多、厂商域名等；只描述位置，不代替证据。

每条属性、绑定或规则可以关联多条来源，标记“提出 / 支持 / 反驳 / 修订”的关系。模型提出应记录模型及运行 ID；网页来源必须有实际抓取 URL 和可定位摘录；Excel 参考记录文件 hash、Sheet、行和字段。没有查到资料就标待核验，不能填“来自某电商行业标准”。

评判依据采用可扩展代码表：业务用途、类目适用性、语义独立性、口径明确、可获取性、单位合理、公式成立、枚举覆盖、来源支持。判定值另设通过/需修改/拒绝/待补证。所谓“符合常理”只能作为弱支持，不能替代证据。

## 6. 首期生成流程与任务粒度

| 阶段 | 输入 | 产出与通过条件 |
|---|---|---|
| 1 范围解析 | 根类目 ID、固定树 | 真实末级清单、相邻边界；同名节点不合并 |
| 2 参考准备 | 分支、参考索引；样本策略待确认 | 可定位来源包；资料中的指令不执行 |
| 3 建模维度 | 类目含义、用途、参考包 | 维度树、共性/差异、容易混淆的计量范围 |
| 4 候选属性 | 维度树 | 每项名称、定义、类型、用途、来源关系；本阶段就决定基本类型 |
| 5 完整属性卡 | 候选、公共定义 | 明确绑定、单位、枚举、公式、前提、缺失处理与例子 |
| 6 程序校验 | 属性卡 | ID/类型/单位/枚举/公式合法，跨卡重复与冲突检查 |
| 7 语义复核 | 卡、证据、评判标准 | 专项问题清单，引用具体字段；不把一致当准确率 |
| 8 定点修复与裁定 | 问题清单 | 只重做受影响卡；无法解决保留待确认 |
| 9 冻结与报告 | 合格产物、遗留问题 | 版本化属性卡、理由、来源、成本；再与旧版盲后对比 |

一个叶类的一次属性卡生成可以包含该类多个相关属性，不给每个字段单独发一次请求。公共定义在分支内先统一，再并行生成叶类绑定；后续修改公共定义时，只让依赖它的卡重新验证。例子与边界检查由独立复核任务处理，仍然是同一模型家族的审核，不能称模型间独立交叉验证。

修复次数有上限，超过进入问题队列；不能以“修到所有检查通过”为由无限调用。断点缓存以类目、阶段、输入 hash、标准 hash、模型配置组成任务键；有效结果复用，失败与结果未知分开处理。

## 7. 上下文与缓存

上下文顺序：系统角色/安全规则 → 已发布建模标准 → 输出 Schema → 分支共用资料 → 当前任务与输入产物。

稳定序列化、固定字段顺序、零缩进有助于前缀复用。DeepSeek 缓存是已落盘前缀的复用，不等于存了文档以后请求就可以省略正文；命中仍占上下文并产生相应输入成本。缓存默认启用、尽力而为，必须记录返回的命中/未命中用量。见[官方缓存说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)。

本地实测：`mapped-tree.json` 包含 13,587 个新树节点，以及旧树、映射等；零缩进约 10.37 MB。仅提取新树 ID、父 ID、名称、末级标记仍约 1.84 MB，此为结构投影，不是全部原数据的无损压缩。

当前清洁纸品根 ID 为 `8ee638a9-2cd7-4bf4-ac31-536b6a3a1f5d`，按父子关系遍历得到 25 个节点、21 个末级；这部分结构投影约 3.3 KB。另有同名四级类目，故入口 ID 必填。

做法：完整原件冻结保存；核心标准必须随任务输入，不能只给一个无人读取的索引。相关分支结构常驻上下文；完整节点、相邻边界、长参考文档通过已登记只读工具获取，并记录实际读取的版本。丢字段的投影和对文本的摘要必须明确标识，不能称无损。

每个任务带阶段、上游产物引用、当前目标、阻断项与下一步条件，不传整个历史聊天。工具返回核心定义的原文；证据长文可以分段定位，保留可回溯的原文。

## 8. 并发与费用控制建议

官方当前 Flash 账号并发上限为 2,500，Pro 为 500；Search 100 QPS，Fetch 25 QPS。不同接口分别限流。[模型限速](https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit/)、[搜索限速](https://api-docs.deepseek.com/zh-cn/guides/search/)。

建议入口提供 `--category-id`（必填）、`--concurrency auto|N`、`--max-concurrency`、`--budget-cny`、`--max-output-tokens`、`--resume`。这里是接口设计，不是现成可运行命令。

auto 建议从 8 个真实任务起步，观测完成吞吐、P95 延迟、429/超时率、结构合格率后逐级提高；遇到错误降速。当前只有 21 个叶类时，不制造无用任务来冲满并发。真正依赖上一步的阶段必须等上游通过，不能全部同时发出。

统一预算涵盖生成、修复、检索、抓取；并发发出前原子预留预算，再按实际用量结算。402 停队列；明确可重试错误有限退避；网络断开但服务端结果未知时单列，避免盲目重复收费。缓存命中不意味着输出免费，需同时控制回复长度和修复轮数。

## 9. 建议目录与最少准则

下列为设计布局，当前只创建本 README、术语与架构讨论稿。

```text
product_governance_v2/
  standards/             # 目标、建模、取值、来源、评审、版本规则及索引
  domain/                # 定义/绑定/规则/证据/流程的统一契约
  tools/                 # 原文读取、类目查询、参考检索、规则计算
  providers/deepseek/    # Responses、Search、Fetch、Balance 统一封装
  context/               # 版本化上下文装配、稳定序列化、依赖追踪
  workflows/             # 阶段定义、输入输出与完成条件
  runtime/               # 任务队列、并发、预算、断点、重试
  reports/               # Excel、评估、旧版对比
  tests/                 # 业务反例、计量/边界/状态验证
  docs/                  # 架构与决策记录
```

准则首期只需六份：业务目标与范围、属性建模、取值与计量、来源证据、评审与验收、执行与版本。Markdown 描述业务理由，机器契约承载可校验结构；索引只引用唯一版本，不能在提示词、导出脚本和校验器各抄一份。

## 10. 首个可验证成果

已确认先用软包抽纸、湿纸巾、纸巾盒检验三种不同建模形态，每类 10 件原始商品资料辅助，再跑完整 21 类；总范围不改变。交付同一个 Excel 的属性卡、来源、评审修改、疑点与成本页，同类目相邻排列，ID/完整路径等定位列前置。

首期检查指标：结构合格率、语义问题及修复率、来源可核验情况、每类成本/耗时、缓存命中、重试与人工处理量。尚未填写商品时不报填充率，未经人工抽检不报准确率。

属性卡冻结后再打开旧答案比较新增/遗漏/定义差异，标明这是回顾比较。后续如据此修订，发布另一个版本，不污染首轮从零生成的评估。

商品归属、值填写与回归只预留对象契约：归属结论及目标 ID、带证据的字段值、适用性与缺失原因、评估分母。执行这些阶段另行推进。

## 11. 实施顺序与完成依据

1. **标准与模型**：六份准则、统一业务契约和工具索引，能够从同一来源生成校验与模型上下文；这里不预置旧21类属性答案。
2. **运行底座**：官方调用器、类目ID遍历、稳定上下文、有限工具调用、并发队列、累计预算和断点；用离线测试验证重复任务复用、预算预留和失败状态，再做计入预算的最小实际接口验证。
3. **三类闭环**：样本筛选、参考收集、维度/候选/完整卡、程序校验、每类完整DS复核、定点修复、Codex异常裁定和抽查；交付首版Excel与真实用量。
4. **铺满21类**：先修复共用问题并重验受影响的三类结果；按剩余预算估算扩围，用同一流水线完成其余18类。未解决问题明确保留，不通过提高并发掩盖质量问题。

首轮完成依据是可复核的属性建模结果与过程记录；不据此宣称商品填充或线上治理已经完成。
