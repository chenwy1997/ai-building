## 3. 初步根因判断（推断，待共同修正）

1. **成功标准停留在候选产物层。** 生成了卡、通过了结构检查、导出了Excel，与实际后台可承载、运营可审核、采购可使用之间，缺少共同验收合同。
2. **业务边界在生成后才被纠正。** 模型遵循的规则反向要求品牌、条件必填、单位拆分和固定布局；局部修补没有改掉问题来源。
3. **属性被当作类目内清单，关系未成为主要输入和验收对象。** 已有节点上下文和单位附件，但不足以约束同族共同定义、共同配置与差异理由、维持完整参数表达；类目名称包含某特征不能成为自动删属性的理由。
4. **审核方法有流程证据，缺少能力证据。** 生成器与审核器共享盲区；提示、模型一致和单元测试不能单独证明符合人的要求。
5. **研发内部缺少用真实任务验收的循环。** 缺少人工判错案例、专业来源准入、小屏操作任务、发布变更回读等可重复的检验。
6. **规范的发布与执行链未贯通。** 标准、schema、知识包、检查器、系统映射和交付文件没有组成完整的一致版本。
7. **部分规则与检查没有成为真实执行入口的必经步骤。** 较严格计算函数仅由测试调用，实际试填只复算模型给出的操作数，后期小样本又使用不同契约。规范需说明每条规则在哪一步执行、输入证据是什么、程序与语义审核分别能验证什么，并覆盖真正产生交付的入口。

经验闭环的候选形式：案例证据 → 提炼适用条件与反例 → 写入一个权威规则位置 → 确认模型确实读取 → 确定性检查或人工基准验证 → 对实际交付做使用验收。不能把每个案例都变成新提示词例外。
