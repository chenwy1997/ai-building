# 属性产生顺序与任务交接 v1

这是后续新任务的共用业务上下文。它规定模型应如何工作，不表示调度器已经实现了所有阶段；实际能力、缺口和运行配置见 `docs/runtime-efficiency-audit-20261020.md`。已冻结任务继续用其原标准，不能为应用本规范而重跑已完成商品。

## 1. 公共定义先行，类目绑定分别判断

在确认任务类目范围后，优先检查公共识别属性，例如品牌、型号/货号。已有经确认的公共定义先检查适用性；没有定义时由DeepSeek提出完整候选并审核一次，固定版本后供各类目引用。公共定义与类目特性同时遵守命名、字段类型、证据和取值规则。

“公共属性”标签与“已共享定义”不是同一概念。只有显式登记为共享的定义才能跨类目复用；其他候选仍以类目ID和属性ID联合定位。同名不强制合并；颜色、尺寸、数量等不能仅因常见就统一对象和口径。公共属性在本类是否适用、是否必填、承载于SKU还是SPU，均由该类绑定独立判断。

公共定义已经确认时，不让每个类目重新改写定义。模型只建议本类绑定或提出带理由的公共变更请求，公共变更影响所有依赖，不能局部覆盖。

## 2. 从业务问题递进形成属性

每个末级类目按以下顺序形成可交付的业务依据，不能只交一张字段名称列表：

1. **对象与边界**：产品是什么，排除什么，相邻类目如何区别；明确纸本体与分配器、单品与组合包装等差异。
2. **原始样本归属**：已挂载不等于归属正确。标题、规格足以确认符合的样本可辅助建模；错挂样本隔离，待确认样本标记，不能用其特性扩充本类枚举。
3. **业务维度**：识别、材料结构、用途性能、尺寸、包装计量、其他可选特性；每个维度说明业务目的，不适用的维度省略。
4. **属性候选**：回答该维度中的具体问题，同时给出名称、定义、类型、业务用途和提出依据；有证据的差异用于完善枚举，不从个别样本推断穷尽范围。
5. **建模与关系**：落实描述对象、单位、必填条件、SKU/SPU、枚举、规则、来源；数量与计数单位、每包与销售总量、适用形态等关系必须明确。
6. **反例检查**：用抽与张混淆、销售总量当单包、配件尺寸当纸张尺寸等反例检查定义和规则。合成例子必须标明，不能伪装来源事实。

无需输出内部思维过程，只记录简短业务理由、维度归属、引用和结构化依赖。维度分组、字段覆盖和依赖可校验，不代表模型具备完整业务理解或结果必然正确。

## 3. 生成、审核与定点修复

- 生成阶段就应用全部核心准则，包括命名与本地参考适用性；不把命名规范、公共属性确认留到批量完成后再全量返工。
- 程序先检查结构、类型、真实ID、来源引文、维度覆盖、单位和规则引用；DeepSeek再对每类做一次完整语义复核。
- 修复仅返回受影响定义/绑定/规则及必要依赖；未变项不重复生成，原始来源不可改写。
- 修改后重验变更项及依赖；发现可复用的错误模式先固化共用规则，再重验受影响范围。
- 未解决项转异常清单；不通过循环改名、删除核心字段、降低必填或无依据填值消除问题。
- 程序通过、模型复核通过、Codex裁定、运营验收是不同状态。自动任务完成不表示已获准发布线上。

## 4. 每步都交代上下文

任务输入应包含本阶段、前置结果版本、当前目标、允许修改范围、所用标准版本与来源索引。产物记录下一步、未解决项、定义与绑定引用；不能只输出“完成”。

核心准则必须实际提供给模型；大资料可用可解析的索引按需读取。必须有工具读取能力才允许仅传索引，不能假定模型看过未提供的全文。同一个运行内标准版本冻结。
