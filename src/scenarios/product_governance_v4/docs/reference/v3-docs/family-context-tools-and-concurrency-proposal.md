# 同族上下文工具与并发协作：设计建议

日期：2026-10-22。状态：保留接线前的讨论稿。依据已确认的Q6（先同族基线后末级差异）、Q8（按商品识别同族，可跨父节点）、Q9（关键业务判断决定必填）、Q10（首批同族分组纳入人工样板验收）及Q11（候选基线供本批产生待审草案）。现已实现只读检索、固定快照中的基线状态和离线工具循环；跨批原子占用、同族发布协调和语义归族仍未实现，实际能力见[v3说明](../README.md)。下文第2节源码路径相对于`product_governance_v2`，描述当时的核查事实；拟议接口不能直接当成当前可执行命令。

## 1. 要解决的业务问题

新类目建模前，需要找到已有的同族标准、相近类目和可复用定义；同一批次或不同批次同时工作时，也要知道哪些基线正在生成。每类都独立查找、未命中就另起一套，会再次产生同义属性与不同配置。

相似不等于同族。检索负责找候选，归族负责核对商品对象、主要结构、用途、选型参数及不适用反例。稳定的同族身份应被复用，不能由每个模型请求随意另起ID。

## 3. 职责分工

- **领域工具**：按结构化条件查类目、属性池与基线，读取指定版本和生成状态，登记修改提案；返回可追溯结果和明确错误。
- **业务skill**：指导如何判断同族、核对属性含义与计量口径、识别交叉重复、解释差异。与生成器、审核器引用同一套权威业务规则，避免各自维护相冲突的标准。
- **批处理执行脚本**：强制必需的上下文检索，调度共同基线和末级差异任务，固定输入版本，协调占位、预算、失败恢复及状态。

先封装项目内的结构化工具接口，同一实现可供脚本直接调用，也可通过适配层供模型按需调用。必须的前置检索由执行脚本保证；模型按需补查用于解决进一步疑问。模型未主动查询不能成为绕过前置上下文的途径。

## 4. 建议的工具契约

以下为拟议名称，不能作为已可运行的命令使用。

| 工具 | 主要输入 | 返回内容与边界 |
| --- | --- | --- |
| `find_related_categories` | 目标类目ID、类目目录版本、业务对象/用途线索 | 返回已登记同族及其他相关候选、真实ID/路径、相关理由、差异或反例；标明已确认成员与待判断候选 |
| `get_family_context` | 同族ID、指定基线版本或明确的版本选择条件 | 返回成员及理由、基线定义、末级差异、确认状态、生成任务状态、来源与版本；生成中的任务只提供状态，不冒充完成的定义 |
| `search_attribute_pool` | 概念及别名、描述对象、计量范围、用途、属性池快照 | 返回候选定义、单位/枚举、适用类目、确认状态及匹配差异；命中名称不能自动判为可复用 |
| `propose_baseline_change` | 同族与原基线版本、拟议增删改、业务理由、受影响类目 | 登记变更提案并返回提案ID；基于陈旧版本的提案必须暴露版本差异。它不由某个末级任务直接改写已确认基线 |

每次检索保留检索范围、目录/属性池版本、命中结果与实际采用项。未命中、读取失败、仍在生成是三种不同结果。是否采用、为何不采用应能回到实际定义和业务理由，不只保留一个相似度分数。

检索可以从树关系、名称、别名及定义摘要发现候选，再核对语义；具体检索实现应通过代表案例评估跨父节点漏召回和错误归族，不能预先宣称已解决所有同族识别。

## 5. 生成顺序与并发

建议顺序：选定任务范围 → 检索目录与属性池 → 解析同族身份并规划依赖 → 取得约定可用的基线版本 → 并发产生末级差异 → 同族整体差异复核。

| 查到的状态 | 建议动作 |
| --- | --- |
| 有符合当前规范与范围的可用基线 | 显式固定版本，末级引用共同定义并提出局部差异 |
| 同一基线任务正在生成 | 关联该任务并等待明确结果，不能把尚无产物误判成不存在 |
| 已有待审候选 | Q11已确认可固定版本供本批产生待审草案，依赖结果一同待审；确认前不进入其他批次默认标准 |
| 没有可用基线 | 协调登记唯一的基线任务，完成后释放依赖任务 |
| 检索或读取失败 | 保留失败状态并处理，不能退化成未命中后自行建另一套 |

不同商品族的基线可以并发；每个族的基线达到约定可用状态后，其末级差异可以并发。并发32代表最多32个满足前置条件的任务在执行，不意味着32个末级都必须从空白开始。

单独治理一个末级时，可以读取其他类目的目录和已登记基线作参考；检索到其他类目不自动授权扩大商品生成、补填、迁移或线上变更范围。

## 6. 防止两个批次各建一套

- 所有运行查询同一个同族与基线登记目录；不能只各看自己的run输出目录。
- 在领取基线创建任务前先解析规范化的同族身份。候选族的重复登记也需协调核对；如果已误认成两个familyId，给familyId加锁本身无法解决语义重复。
- 对同一同族、同一规范版本的基线创建/修订设置唯一协调者。相同输入返回同一任务；不同输入登记为修订或冲突，不覆盖同一个已固定版本。
- 查询与领取任务必须是一个有互斥保证的操作，避免两个任务都先查到不存在、随后各自创建。当前临时文件加rename只能避免半个文件，不能独立保证这项业务约束。
- 任务失败要有明确状态和恢复路径。等待者不能因任务超时就各自重建一套；恢复须保留输入、版本与费用记录。

具体持久化和并发原语尚未选定，先确定上述行为约束。

## 7. 共享基线的变更

Q13已确认以下业务流程；具体工具与执行接线尚未实现。

末级任务返回引用、绑定与有依据的差异。发现共同基线缺项或定义有误时，登记提案，集中核对受影响成员，再形成新版本。运行中的其他任务保持其固定输入，不随某个任务的完成顺序偷偷改变含义。

集中处理发生在研发流程内，不要求运营对每次研发修订逐条批准；正式采用仍按业务验收。局部确有不同的业务需要时，保留明确差异及理由，不覆盖其他类目的共同定义。

同族一致性检查覆盖共同定义、名称、类型、单位、计量范围、枚举及必填差异的理由；数目相同不证明一致，同名也不证明同义。确认基线修订后，仅安排受影响的依赖检查，不默认重跑全站。

## 8. 后续验收应覆盖的反例

1. 有芯/无芯小卷纸能命中同族，并使用同一套共同定义。
2. 语义相近但在不同直接父节点的类目仍能被检索到。
3. 纸巾与纸巾盒被找为相关候选时，能够说明对象差异，不直接共用纸品基线。
4. 两个独立批次同时请求相同同族时，只出现一个创建任务和一个规范化身份。
5. 基线生成中、失败、已完成、待审等状态不会被当成同一种未命中。
6. 同名不同计量范围、净重与含芯/包装重量等概念不会仅凭名称被合并。
7. 基线修订与旧任务并存时，结果准确标明所引用版本，不混用定义。
8. 复用了现有标准的类目可以指出使用了什么、拒绝了什么及原因；只在工具说明列出检索名称不算实际调用。

## 9. 同族分组的人工样板

Q10已确认：首批同族成员判断和分组理由纳入人工验收。样板包含应归为同族的案例及相关但不应同族的反例，用于分别观察误合并与漏发现。首批样板校准后，再讨论自动归族范围，不预设已经具备自动放行能力。

## 10. 候选基线的使用范围

Q11已确认：待审共同基线可以固定版本供本批生成末级待审草案，再集中审核共同属性与末级差异。所有依赖结果都保留待审状态，未经业务确认不进入其他批次默认标准，也不据此启动线上变更。正式复用与发布的具体门槛还需后续细化，冻结输入只代表本批保持一致。

Q13已确认共享定义的变更权，见第7节。Q14已确认专业类目使用可复用领域知识包；后续工具返回的属性和同族上下文也需要能够追溯所引用的专业资料与知识版本，具体契约继续细化。
